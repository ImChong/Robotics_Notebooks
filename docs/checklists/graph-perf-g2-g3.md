## 3. 2D：筛选态（Top 300）—— G3 的主战场

G0 第 5 节实测确认：Top N 此前只改 opacity 与 pointer-events，力计算与 DOM 规模**完全不变**。

| 指标 | 前（2 轮） | 后（3 轮） | 变化 |
| --- | --- | --- | --- |
| `simulation.nodes()` | 3,868 / 3,868 | **300 / 300 / 300** | 真实子图 |
| `forceLink.links()` | 34,420 / 34,420 | **3,435 / 3,435 / 3,435** | 真实子图 |
| 力 tick p50 | 69.2 / 69.4 ms | **4.2 / 4.3 / 4.3 ms** | **约 16 倍** |
| DOM 同步 p50 | 191.2 / 166.5 ms | **14.7 / 15.1 / 14.1 ms** | **约 12 倍** |
| **每 tick 合计** | **≈ 260 / 236 ms** | **≈ 18.9 / 19.4 / 18.4 ms** | **约 13 倍** |
| `applyFilters()` p50 | 136.3 / 126.2 ms | 129.2 / 131.0 / 127.7 ms | 持平 |

**每 tick 合计首次接近 16.7 ms 帧预算**（18–19 ms，约 53 FPS 的预算占用）。
`applyFilters()` 持平是预期的：G3 的子图重建成本换掉了谓词求值的节省，两者大致抵消；
它不是每帧调用，且滑块输入已由 G1 按帧合并。

## 4. 2D：全图态 —— 未达标，剩余属 G4/G5

| 指标 | 前（2 轮） | 后（3 轮） | 变化 |
| --- | --- | --- | --- |
| 力 tick p50 | 69.1 / 72.6 ms | 72.7 / 74.6 / 73.7 ms | 无变化（未触碰力计算） |
| DOM 同步 p50 | 202.4 / 179.1 ms | 156.9 / 134.1 / 128.8 ms | **约 −25%～−36%** |
| `applyFilters()` p50 | 110.1 / 124.0 ms | 120.1 / 115.7 / 104.5 ms | 区间重叠，记为持平 |
| 每 tick 合计 | ≈ 271 / 252 ms | ≈ 230 / 209 / 203 ms | 约 −18% |
| 首屏就绪 | 4,716 / 4,671 ms | 4,050 / 3,978 / 4,395 ms | 约 −9% |

全图 DOM 同步的降幅是 G3 顺带拿到的：`syncGraphDomFromSimulation` 由三趟 d3 选择集
（`.attr(x1/y1/x2/y2)` + `.attr(transform)`）改成按数据数组直写属性。

**全图态每 tick 仍约 203–230 ms，远未达 16.7 ms 预算**，本次不声称解决全图动态。
每 tick 141,548 次坐标属性写入（`4 × 34,420 + 3,868`）这一结构量没有变，
它是 **G4（2D 改 Canvas）** 的范围。

## 5. 3D：悬停与标签 —— G2 的主战场

| 指标 | 前（2 轮） | 后（3 轮） | 变化 |
| --- | --- | --- | --- |
| 悬停刷新 `hover_on` p50 | 403.1 / 357.2 ms | **21.1 / 18.0 / 22.5 ms** | **约 19 倍** |
| 取消悬停 `hover_off` p50 | 368.4 / 328.9 ms | 17.9 / 17.8 / 18.4 ms | 约 19 倍 |
| `syncLabels()` p50 | 346.0 / 282.9 ms | **12.7 / 13.1 / 14.5 ms** | **约 24 倍** |
| 标签 DOM 元素数（标签关闭时） | 3,868 | **0** | — |

根因不是渲染，是**与可见性无关的全量 DOM 写入**：节点名称开关默认关闭且浮窗入口已隐藏，
但每次进入 3D 仍预建 3,868 个 `div`，`syncLabelStyles` 又无差别为全部元素写
`textContent / color / fontSize / classList`；而 `refreshAppearance()` 每次悬停都会调
`syncLabels()`。于是「悬停一个节点」要付一次全量标签同步的代价 —— 346 ms 里占了 403 ms 的大头。

第二项（`scene.traverse` → `__threeObj`）在此基础上再降约 24%（24.9 → 19.0 ms，单独测得）。
悬停会把全部非邻居节点统一淡化，逐节点不透明度**本就是 O(节点数)**，这里减掉的是
「白跑一遍 34,420 个连线 mesh」，不是把节点更新也变成增量。

功能回归：悬停最高度数节点（Manipulation）时 1,274 亮 / 2,594 暗（= 自身 + 1,273 邻居），
清除悬停后 3,868 全亮，与改动前语义一致。

## 6. 3D 连线细线：实测否定，不实施

计划中 G2 含「3D 普通边试用细线」，G0 第 7.4 条据 38,272 draw calls 推测
「边改细线（`LineSegments` 合批）可望把边的 34,409 次调用降到个位数量级」。
本次按 `linkWidth → 0` 做了一次可回滚的实测尖峰（spike），结果**否定该推测**：

| 指标 | 圆柱（现状） | 细线（spike） |
| --- | ---: | ---: |
| 每帧 draw calls | 38,288 | **38,287** |
| 每帧三角形数 | 1,661,568 | 835,272 |
| `lines` | 0 | 34,420 |
| 几何体数 `memory.geometries` | **2** | **34,421** |
| 悬停刷新 p50 | 19.0 ms | 19.9 ms |

原因在库内：`three-forcegraph` 的 `onCreateObj` 里，`linkWidth` 为 0 时创建的是
**每条边一个 `THREE.Line` + 一份自己的 `BufferGeometry`**，不是共享的 `LineSegments`。
所以细线：

1. **不减少 draw calls**（38,288 → 38,287，差 1 属视锥剔除抖动）；
2. 三角形数减半而非归零 —— 剩下的 835,272 就是 3,868 个节点球（3,868 × 216 = 835,488，与实测吻合）；
3. **几何体数由 2 涨到 34,421**：现状的圆柱几何是共享的，改细线反而让每条边各持一份 VBO；
4. 高亮加粗会失效 —— 现状靠 `linkPositionUpdate` 缩放圆柱半径轴实现，`Line` 没有半径可缩放，
   要保住「高亮边独立粗线覆盖」还得再补一套 overlay。

**结论：细线在本仓库当前库版本下是净负收益，不实施。**
真正能把 34,420 次调用降下来的只有「自建一个合并的 `LineSegments`」，那是 **G6（连线批绘制）** 的范围；
G0 第 7.4 条应据此修正 —— 合批收益成立，但**不能靠切换 `linkWidth` 顺带拿到**。

## 9. 由本次实测得到的结论

1. **G3 成立且收益最大**：筛选态每 tick 由 ≈ 260 ms 降到 ≈ 19 ms，首次接近帧预算。
   G0 第 7.2 条「G3 性价比最高」得到验证。
2. **3D 悬停的瓶颈不在渲染，在标签 DOM**：403 ms 里 346 ms 是与可见性无关的全量标签同步。
   这类「开关默认关闭、代价却照付」的路径值得在别处也排查一遍。
3. **G0 第 7.4 条需修正**：细线不等于合批，本库版本下切 `linkWidth` 反而增加几何体数。
   3D 侧要拿 draw calls，只能走 G6 的自建 `LineSegments`。
4. **全图态仍未达标**：每 tick ≈ 203–230 ms，每 tick 141,548 次坐标属性写入的结构量没变。
   下一步应是 **G4（2D 改 Canvas）**，与 G0 第 7.1 条的判断一致。
5. 真机 GPU、手机与 Safari 仍未测，3D 帧率不可由本页外推。
