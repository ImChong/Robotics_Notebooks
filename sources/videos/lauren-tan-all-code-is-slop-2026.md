## 一句话要点

高吞吐 coding agent 的前提不是添加更多提示词，而是以良好 API / 架构约束、静态检查、运行时与形式化验证构建可重复的高信任环境。

## 核心机制与因果链

1. **代码即 Agent 的长期示范：** 不良样板、过期兼容代码和旁路注释都会作为上下文，影响下一轮生成；代码库治理直接影响生成质量。
2. **把人类纠错变成确定性约束：** 在代码层消除无效操作的入口，或用 lint、类型、测试拒绝非法选择；自然语言提示保留给需要判断的场景。
3. **让执行结果成为可检查证据：** 功能地图负责统一用户语义，运行工具负责复现行为，视频 / 截图 / trace / 状态图与形式化检查负责验证不同性质。
4. **先内环再外环：** 一个会反复产生错误的工作流，自动扩张只会放大错误及 token 维修成本。

## 案例、数字与边界

- **Dune 的 useEffect 限制是局部工程策略：** React useEffect 并非普遍错误；演讲指该团队只允许框架内部特定接口使用。
- **进程边界限制：** main 与 renderer 目录和静态依赖规则可提前发现会造成 UI 卡顿的错误导入。
- **关于注释：** 演讲自述在团队产品代码中禁止约 99% 的注释；这是特定系统的做法，不能推导为所有项目都应禁用文档和注释。
- **关于 70%：** 属于演讲援引另一名工程师 Cindy 的 token 使用比例；Lauren 的原话是自己也把大部分 token 花在验证。
- **关于 11,000/0.5%：** 属于讲话人报告的团队产出和 revert 比例；revert 率不能覆盖那些以新 PR 修复的缺陷，也不能单独代表事故率或正确性。
- **关于自动合并：** 演讲展示的是依赖已有工程约束的团队流程，不意味着机器人控制/安全关键软件可以无审查上机。

## 面向 Robotics_Notebooks 的可迁移结论（编辑者推论）

- **把日常 agent 纠错沉淀为脚本与测试。** 重复的 wiki 缺链接、原文校验、Mermaid 错误应以 lint/CI 明确拒绝，而不是在 AGENTS.md 中无限追加解释。
- **把健康度、CI 绿灯与事实正确性分开。** 结构化 3/3 是质量信号之一；来源核验、内容去重与机器人真机安全必须另有可复核证据。
- **让机器人代码也拥有双重验证。** 控制接口约束、静态检查用于防错；SIL/仿真 rollout、真实 IO 时序及安全测试检查动态行为。不能用 Web UI E2E 等价替代硬件安全测试。
- **高风险改动需要差异化审批。** 影响运动控制、关节限位、急停与部署的 PR 应强制人工审核，即使软件层检查全部通过。
